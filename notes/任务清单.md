## ④ 注意事项（踩过的坑，务必记住）

### 数据层
1. **类目命名**：Olist 有两套类目（葡语 moveis_escritorio / 英语 office_furniture），全项目统一用英语，别混用
2. **差评率分母**：用"差评数÷评论数"，不是"÷订单数"（沉默者偏差：没评论≠好评）
3. **多对多归属**：评价是订单级，一单多卖家时"取第一个商品"会漏/错配，query_seller_risk 已改成卖家级聚合
4. **卖家缩写**：用户说"b33"这种短前缀会匹配多个卖家，必须做唯一性检查，匹配到多个就诚实说"不唯一"，不能静默取第一个
5. **结论方向**：不仅数字要对，"谁高谁低、谁快谁慢"的方向也要对（踩过"标价低写成高"的坑）
6. **数字三方对齐**：故事 md / provenance 脚本 / 知识库，三处数字必须一致（已多次踩坑，改了又改）

### 数据边界
7. **数据是 2016-2018 巴西数据**：不能声称代表现在，作品里要诚实标注"用于验证方法论，数值不反映当前"
8. **无实时数据**：Agent 查的是历史 CSV，不是实时物流，回答要标"基于历史数据，仅供参考"
9. **无长期记忆**：只有会话内5轮上下文，关掉重开不记得（这是设计选择，不是bug）

### 安全
10. **API key 不进 git**：.env 已在 .gitignore，提交前务必确认没把 key 提交进去
11. **Notion API 凭证**：之前给过 Notion token，用完已清理，以后别随便发这种凭证

### Agent 设计原则（用户强调的）
12. **不要什么都用固定话术**：capability/methodology 这类应该让 LLM 根据语境动态生成，而不是返回写死的字符串，否则发挥不出大模型的特点
13. **数字不让 LLM 算**：数字一律由 query.py 查知识库，LLM 只负责组织语言（防幻觉的架构保证）
14. **信息分层**：用户侧只给"约/大概/左右"的模糊结论，底层数据（n/P50/P90）放在"推理链路"trace 里给面试官看

## ④ 注意事项（踩过的坑，务必记住）

### 数据层
1. 类目命名统一用英语（office_furniture 不是 moveis_escritorio）
2. 差评率分母 = 差评数÷评论数（不是÷订单数）
3. 多对多归属：评价订单级，一单多卖家要卖家级聚合
4. 卖家缩写短前缀匹配多个 → 诚实说"不唯一"，不静默取第一个
5. 结论方向：数字对还不够，谁高谁低方向也要对
6. 数字三方对齐：故事/脚本/知识库三处一致
7. **cat_avg_return_kw ≠ 差评基线**（那是退货词均值，差评基线用 category_baseline.neg_rate）
8. **卖家 ID 不是卖家州**（query_timing 传 seller_id 永远匹配不到，先 query_seller_state 反查）

### 评分与口径
9. **min-max 归一化抹平绝对差距** → 用相对比例 score = min/value
10. **neg_rate 双口径**（seller_risk vs seller_cost），评分统一从 seller_risk 取
11. 卖家级差评原因样本稀疏 → 诚实标注或回退品类，不编造

### V2.0 新增踩坑
12. **sort_direction 不能一刀切**：ship_time 类"排名"默认 asc（最快），freight/price/neg_rate 默认 desc（最贵/最差），回答方向必须和排序一致
13. **能力矩阵格子要两操作都做**：route×freight 做了 aggregate 漏 query，导致"MS送到SP运费"查不到
14. **recommend 数据要丰富**：只返回哈希 ID 会让 LLM 空谈 + 编造，必须补 seller_city/seller_state
15. **多对象循环是通用逻辑**：多卖家只查第一个是打补丁，应在 dispatch 层统一"多值→循环对比"，覆盖所有指标和维度
16. **capability 约束要写死**：软约束"不要编造"会被 LLM 忽略，必须明确"只能文字、只能 4 项能力、禁止读链接截图"

### 防幻觉铁律（贯穿 V1 和 V2）
17. 数字不让 LLM 算，由数据层查
18. 缺失维度禁编造（没查价格不说"综合推荐"，没查时效不编天数）
19. 只答用户问的指标，不脑补没问的维度
20. 数据模糊化（约/大概/左右/九成），禁 n=/P50/P90

### 数据边界与安全
21. 数据 2016-2018 巴西数据，标注"用于验证方法论"
22. 无实时数据，标"基于历史数据仅供参考"
23. 无长期记忆（会话内 5 轮）
24. API key 不进 git（.env 已忽略）
25. 特殊品类约束（美妆/母婴/医疗器械/食品/二手）

### 架构认知（用户领悟的关键）
26. **不是 RAG，是结构化查询 + 手工版 function calling**（数据是精确数值，不是文本；LLM 分类 + 代码路由，不是 LLM 自主选函数）
27. **prompt + LLM 语义理解**：框架写死（有哪些三元组），判断靠理解（这句话归哪个）
28. **核心从业务逻辑出发**：建数据 = 用户决策链上缺什么信息，不是"数据能算什么"

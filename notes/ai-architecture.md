# AI 架构设计 — 懂履约的 AI 购物助手

> 目的：补齐评审漏洞 4（AI 产品设计深度）——模型选型、Prompt 模板、多轮对话、工具调用、错误处理。
> 这份文档也是搭原型的"图纸"（阶段 3）。

---

## 一、整体架构（四层）

```
用户提问
  ↓
【对话层】多轮上下文管理
  ↓
【意图识别层】LLM 判断：时间 / 风险 / 成本 / 其他
  ↓
【工具调用层】LLM 选工具 → 查履约知识库
  ↓          ↑
【数据层】履约知识库（route_timing / seller_risk / seller_cost / category_baseline）
  ↓
【回答生成层】LLM 把数据组织成人话 + 诚实兜底
```

**核心原则（贯穿全程）：数字只由数据层计算，LLM 只负责"听懂 + 说人话"。**

---

## 二、模型选型

| 用途 | 选型 | 理由 |
|---|---|---|
| 意图理解 + 回答生成 | 一个主流 LLM（Claude / GPT / 国产大模型） | 意图分类和语言生成是 LLM 强项 |
| 数字计算 | **不用 LLM**，用结构化查询 | 精确计算是 LLM 短板，且不可复现 |
| 落地平台 | 抖音电商 → 考虑豆包/云雀（平台内模型） | 成本、延迟、合规、与平台技术栈兼容 |

**选型考量清单**：中文能力、推理成本（token 单价）、延迟（购物场景要求快）、是否平台生态内。

## 三、Prompt 设计（3 个核心模板）

### Prompt 1 · 意图分类

```
你是一个意图分类器。用户在网购，请判断他关心哪个决策维度：
- time：能不能按时到、多久到
- risk：这家店靠不靠谱、退货方不方便
- cost：哪个更值、到手价、运费
- other：其他（闲聊/售后/不在范围内）

输入用户问题，只输出 JSON：
{"intent": "time|risk|cost|other", "reason": "简短理由"}
```

### Prompt 2 · 工具选择

```
你是购物助手。根据用户意图和已有上下文，从以下工具中选择要调用的：
- query_timing(卖家州, 买家州, 类目) → 配送时效分布
- query_seller_risk(卖家, 类目) → 差评率、退货信号、类目对比
- query_cost(卖家, 类目, 买家州) → 到手价、运费

输出 JSON：
{"tool": "query_timing", "params": {...}}
如果数据不足，标注缺什么字段。不编造。
```

### Prompt 3 · 回答生成

```
你是懂履约的购物助手。以下是查询到的结构化数据：[插入数据]

请按规则组织回答：
1. 先给结论
2. 给数据依据（P50/P90、占比、样本量）
3. 标注不确定性（样本小、代理信号、非实时）
4. 决定权交回用户（"如果你…可以…"）

铁律：只基于提供的数据回答，不得编造或推算。
```

## 四、工具调用设计（tool schema）

### 工具 1 · query_timing
```json
{
  "name": "query_timing",
  "description": "查询某路线配送时效分布",
  "params": {"seller_state": "卖家州", "buyer_state": "买家州", "category": "类目"},
  "returns": {"n": "订单数", "median_days": "中位数", "p90_days": "P90", "pct_in_10d": "10天内占比%"}
}
```

### 工具 2 · query_seller_risk
```json
{
  "name": "query_seller_risk",
  "description": "查询卖家退货/差评风险信号",
  "params": {"seller_id": "卖家", "category": "类目"},
  "returns": {"n_reviews": "评论数", "neg_rate": "差评率%", "return_kw_rate": "退货词占总评%", "cat_avg": "类目基线%"}
}
```

### 工具 3 · query_cost
```json
{
  "name": "query_cost",
  "description": "查询卖家到手价（标价+运费）",
  "params": {"seller_id": "卖家", "category": "类目", "buyer_state": "买家州"},
  "returns": {"n": "订单数", "avg_price": "标价", "avg_freight": "运费", "avg_total": "到手价", "median_days": "配送中位", "neg_rate": "差评率%"}
}
```

### 一次完整的 function calling（多轮示例）

```
用户：这个音响能 10 天内到吗？我在 RN
→ 意图：time
→ 调 query_timing(SP, RN, audio)
→ 返回：n=332, median=18, p90=28.2, pct_10d=11%
→ 回答："到你这平均 18 天，只有 11% 能 10 天内到——大概率来不及。"

用户：那 PE 那家呢？
→ 【多轮上下文】记住"用户在问音响到 RN"，这次调 query_timing(PE, RN, audio)
→ 返回：n=4, median=7.2, pct_10d=75%
→ 回答："PE 那家 75% 能 10 天内到，但样本只有 4 单，仅供参考——建议私聊确认。"
```

## 五、多轮对话设计

**需要跨轮传递的状态：**
1. **意图**（用户一直在问时效？）
2. **已确认的约束**（预算、收货地、品类）
3. **历史工具结果**（避免重复查）

**上下文结构：**
```
session_context = {
  "intent": "time",
  "constraints": {"buyer_state": "RN", "category": "audio"},
  "history": [{"tool": "query_timing", "params": {...}, "result": {...}}]
}
```

**歧义处理**："这家店怎么样" → 不确定是问时间还是风险 → 追问一句"你是想了解时效还是售后？"（对话式消歧）。

## 六、错误处理与降级策略

| 场景 | 降级策略 |
|---|---|
| **API 超时** | 重试 1 次 → 仍失败则告知"暂时查询失败，请稍后再试" |
| **数据为空** | 层级回退到更粗粒度（卖家→类目→整体）+ 标注置信度 |
| **工具报错** | 明确告知"这个数据暂时拿不到"，不编造替代 |
| **LLM 拒绝回答** | 引导用户换种问法，或转人工客服 |
| **样本过小** | 标注"样本仅 X 条，仅供参考"，不硬下结论 |
| **用户情绪化** | 共情 + 回归问题，不敷衍 |

## 七、防幻觉与数据纪律（架构级保证）

1. **数字不进 LLM 的"嘴"**：所有数字由数据层产出，LLM 只引用，不计算；
2. **可复现**：数据来自 `analysis/story*_provenance.py`，口径一致；
3. **诚实标注**：代理信号、样本量、非实时，主动说明；
4. **Eval 兜底**：评测集检测"幻觉率 < 5%"（见指标设计）。

---

## 八、可观测性设计（线上怎么知道出问题）

| 维度 | 指标 | 告警阈值 |
|---|---|---|
| 质量 | 幻觉率（人工抽检） | > 5% |
| 质量 | 意图分类准确率 | < 90% |
| 性能 | P50 响应时间 | > 3s |
| 性能 | P99 响应时间 | > 8s |
| 体验 | 用户追问率（同一意图连续问≥2次） | > 30% |
| 体验 | 用户主动纠正率 | > 10% |
| 系统 | 工具调用失败率 | > 5% |
| 系统 | LLM 拒绝回答率 | > 15% |

**原则**：质量指标靠 Eval 离线测，性能/体验指标靠线上埋点；告警阈值是"先猜后调"，上线后用真实数据校准。

---

## 九、Prompt 版本管理

1. **每个 prompt 有版本号**（v1.0 / v1.1 …）；
2. **改 prompt 前先跑 Eval 回归**，确认不劣化才上线；
3. **线上 A/B 测试新版本**，用真实流量对比；
4. **回滚机制**：保留最近 3 个稳定版本，出问题一键回退。

---

## 十、多轮对话的上下文管理

**上下文压缩策略**（防 token 膨胀）：
- 保留**最近 3 轮完整对话**；
- 更早的对话压缩为摘要，如"用户之前问过 audio 到 RN 的时效"；
- session_context 超过 **2000 token** 时触发压缩。

**意图变更处理**（用户换话题）：
- 每轮重新分类意图；
- 若意图**连续 2 轮变化**，清空 constraints，重新开始；
- 例：用户从"问时效"切到"问价格"，清空之前的时效上下文。

---

## 十一、工具调用的工程细节

**Timeout + 重试**：
- 单工具超时 **2s**；
- 重试策略：**指数退避**（1s → 2s → 4s），最多 2 次；
- 并行调用多工具时，取最慢工具的 timeout，任一失败不影响其他。

**多工具组合**（复杂场景）：
- 用户问"这家店到 RN 要多久？运费贵吗？" → 同时调 `query_timing` + `query_cost`；
- 输出：`{"tools": ["query_timing", "query_cost"], "params": {...}}`；
- 结果聚合后统一回答（对应故事 3 的综合对比）。

---

**面试一句话总结：**

> "我的架构是四层：LLM 做意图理解和回答生成，履约知识库做数据，工具层让 LLM 查数据而不是算数——从架构上杜绝幻觉。多轮对话用 session context 管理，每个场景有降级策略。"

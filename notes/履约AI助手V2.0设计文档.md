# 履约 AI 助手 V2.0 设计文档

> 版本：V2.0 ｜ 状态：已实现（核心功能完成，待 Eval 与网页）

---

## 一、产品定位

「懂履约的 AI 购物助手」：在用户网购下单前，基于历史订单数据，帮助用户判断三个核心问题——**哪个卖家靠谱、多久能送到、多少钱值得买**。

与平台"一刀切"的承诺不同，本助手给出的是基于真实历史履约数据的个性化参考：能精确到"这家店在哪个州发货、发货快不快、送到你那里要多久、平台承诺多久、实际准时率多高"。

---

## 二、系统架构

```
用户问题
  ↓
① 意图识别   将问题解析为三元组（操作 × 维度 × 指标）
  ↓
② 参数校验   按参数必填规则，校验三元组所需的实体参数是否齐全
  ↓
③ 数据查询   按映射表，调用知识库查询函数获取数据
  ↓
④ 回答生成   按回答标准，把数据组织成自然语言
```

**核心原则**：数字全部由数据层计算，LLM 只负责理解问题和组织语言，不参与任何计算。

---

## 三、意图识别：三元组模型

### 3.1 三个轴

**操作（operation）——用户要"做什么"**

| 取值 | 含义 | 示例问法 |
|---|---|---|
| query | 查单个对象某个指标 | "这家发货多久" |
| compare | 多个对象比较某个指标 | "两家谁发货快" |
| aggregate | 某个维度下的统计/分布 | "咖啡平均运费多少" |
| recommend | 按条件筛选排序 | "哪家靠谱" |

**维度（dimension）——用户关心的"主体"**

| 取值 | 含义 |
|---|---|
| seller | 商家 |
| category | 品类 |
| route | 路线（发货州 → 收货州） |

**指标（metric）——用户要"什么信息"**

| 取值 | 含义 |
|---|---|
| ship_time | 发货时长（下单 → 交给快递） |
| transit_time | 运输时长（交给快递 → 送达） |
| total_time | 总时长（发货 + 运输） |
| freight | 运费 |
| price | 价格 |
| neg_rate | 差评率 |
| ontime_rate | 准时率 |
| promise_gap | 承诺偏差（平台承诺 vs 实际） |

### 3.2 三元组输出格式

意图识别不输出单一标签，而是输出结构化三元组：

```json
{
  "intents": [
    {"operation": "compare", "dimension": "seller", "metric": "ship_time"}
  ],
  "entities": {
    "seller_ids": ["b1a812", "5058e8"],
    "category": null,
    "buyer_state": null
  }
}
```

- 一句话涉及多个意图时，输出多个三元组（如"谁发货快，送到 RN 多久" = 两个三元组）。
- 对话类意图（能力介绍、方法论、不支持的功能、无关闲聊）不查数据、不进入三元组，单独处理。

### 3.3 与单标签意图的区别

| | 单标签意图（V1） | 三元组（V2.0） |
|---|---|---|
| 输出 | `time` | `{operation, dimension, metric}` |
| 新增能力 | 加意图标签 + 加代码分支 | 映射表加一行 |
| 能力组合 | 写死在代码里 | 三个轴自动组合 |

| **total_time** 总时长 | ✅ 发货+运输组合 | ✅ 组合 | ✅ 组合 |

**操作能力**

| operation | 处理逻辑 |
|---|---|
| query | 调映射表函数，单对象返回 |
| compare | 对每个对象分别调函数，返回对比列表 |
| aggregate | 调聚合函数，返回分布/top |
| recommend | 按条件筛选 + 排序，取 top |

## 五、参数必填规则

每个「指标 × 维度」组合，都有明确的必填参数。缺参数时按下方兜底话术引导，**不得强行查询或编造数据**。

### 规则总表

| 指标 × 维度 | 必填参数 | 缺参兜底 |
|---|---|---|
| ship_time × 商家 | 商家 ID | 引导提供商家，否则无法回答 |
| freight × 商家 | 商家 + 品类，缺一不可 | 缺什么引导补什么 |
| price × 商家 | 商家 + 品类，缺一不可 | 缺什么引导补什么 |
| transit_time × 路线 | 收货地 + 始发地 | 主动引导收货地址 |
| freight × 路线 | 收货地 + 始发地 | 主动引导收货地址 |

### 逐条说明

1. **ship_time × 商家**：必须指定商家。因为发货时长是商家个体的运营行为，没有商家就无法回答。缺商家时引导："你想了解哪家店的发货速度？告诉我卖家 ID 或名称。"

2. **freight × 商家**：必须同时指定商家和品类。因为不同品类的件型、重量不同，运费报价基准不一致，两者缺一不可。缺商家引导"想查哪家店的运费"，缺品类引导"想查哪类商品的运费"。

3. **price × 商家**：必须同时指定商家和品类。原因同上，不同品类价格差异大。缺商家引导"想查哪家店的价格"，缺品类引导"想查哪类商品的价格"。

4. **transit_time × 路线**：必须同时有收货地和始发地。始发地可由商家信息反查得到。缺收货地时主动引导："你想送到哪个州？告诉我收货地址，我帮你算运输时长。"

5. **freight × 路线**：必须同时有收货地和始发地。规则同 transit_time。

## 七、操作逻辑（四个操作均已实现）

### 7.1 query（查询）

1. 校验必填参数（按第五节规则）
2. 调用映射表对应的查询函数
3. 返回单对象数据

### 7.2 compare（对比）

1. 校验必填参数
2. 对每个对象（通常为多个商家）分别调用查询函数
3. 返回对比列表，按目标指标排序（如发货时长升序 = 最快在前）

### 7.3 aggregate（聚合）

1. 校验必填参数
2. 调用聚合函数（返回某维度下的分布/top）
3. 返回聚合结果

### 7.4 recommend（推荐）

1. 校验必填参数（通常为品类）
2. 筛选：符合条件（如差评率低于类目平均线、评论量足够）
3. 排序：按目标指标排序，取前几名
4. 附加：如有收货地，反查每个推荐对象的发货地并拼上时效

## 八、缺参数兜底标准

| 缺的参数 | 标准答复 |
|---|---|
| 缺商家 | "你想了解哪家店？告诉我卖家 ID 或名称。" |
| 缺品类 | "你想查哪类商品？比如书架、咖啡、美妆等。" |
| 缺收货地 | "你想送到哪个州？告诉我收货地址，我帮你查。" |
| 缺始发地（且无商家可反查） | "是哪家店？我可以帮你查它的发货地。" |

**兜底原则**：
- 全部意图都缺参数 → 合并一次反问，列出所有缺的信息
- 部分意图缺参数 → 有数据的意图正常回答，缺参数的意图单独说明需补充什么
- 缺参数时**绝不强行查询、绝不编造数据**

## 九、回答生成标准

### 9.1 各指标答复标准

**ship_time（发货时长）**
- 正常答复："这家店发货快，一般当天就交给快递 / 大概拖两三天才发货 / 发货偏慢，要一周左右。"
- 模糊化：用"当天、一两天、拖一周左右"，禁止输出精确天数。
- 边界：只讲发货段，不含快递运输时间；缺数据时不编造。

**transit_time（运输时长）**
- 正常答复："快递从发货地运到你这，大概 X 天左右。"
- 模糊化：用"约、左右"，禁止输出精确值。

**total_time（总时长）**
- 拆段回答：先发货段（"这家发货快，当天就交快递"），再运输段（"运到你这大概 X 天"），最后总计（"总共大概 Y 天"）。
- 价值点：让用户分清"慢在发货"还是"慢在路上"。

**freight（运费）**
- 商家维度答复："这家店的运费大概 X 左右。"
- 品类维度答复："这类商品运费一般在 X 左右（占到手价约 Z 成），具体还受重量和距离影响，这是参考值。"
- 模糊化：用"约、左右"，禁止精确到分。

**price（价格）**
- 答复："这家店到手价大概 X 左右（含运费）。"
- 模糊化：禁止精确到分。

**neg_rate（差评率）**
- 答复："这家店差评率约 3%，比同类平均（约 4%）还低一点，比较稳。"
- 模糊化：用"约 3%、不到一成"，禁止输出精确百分比。
- 跨品类：说明哪些品类表现好、哪些差评偏高。
- 差评原因：有数据时说明主要被骂什么；样本少或无文本时，诚实说明"暂时无法拆解"，不编造。

**ontime_rate（准时率）**
- 答复："约九成订单能按时送到。"

**promise_gap（承诺偏差）**
- 答复："平台承诺约 X 天，实际平均 Y 天，约 Z 成能按时到。"（实际普遍快于承诺时强调"实际往往比承诺快"）

### 9.2 模糊化规则（全局）

- 所有数字用"约、大概、左右、九成、大多数、不到一成"等措辞
- **禁止**输出 n=、P50、P90、精确到手价、精确百分比等原始指标

### 9.3 防编造铁律（全局）

- 数字由数据层查询，LLM 不计算
- 缺失维度禁编造（没查价格不说"综合推荐"，没查时效不编天数）
- 样本少时标注"样本仅 X 条，仅供参考"

### 9.4 语气人设（全局）

- **整体语气**：柔和、亲切、带一点俏皮，像一位贴心、友好的购物顾问，不是冷冰冰的机器人。
- **柔和**：不用生硬、命令式的表达。
- **亲切**：多用"你""帮你""咱们"这类拉近距离的词。
- **俏皮**：适度使用语气词和轻松表达（"啦""哦""试试看"），但不油腻、不卖萌过度，不干扰信息准确性。
- **三个典型场景示例**：
  - 正常回答："这家店发货挺利索的，一般当天就交快递啦～"
  - 缺参数引导："告诉我你在哪个州，我马上帮你算算～"
  - 边界拒绝："这个我还真帮不上，不过时效、价格、卖家风险这三样我拿手，要不要试试？"

## 十、通用能力与边界

### 10.1 多轮对话

1. 保留最近 5 轮对话（10 条记录）作为上下文，滑动窗口
2. 追问词（"那、换个、换回、还是"）结合历史补全省略参数
3. 每轮重新识别意图，不沿用上一轮

### 10.2 安全约束

1. 不替用户做最终购买决定
2. 不使用煽动性带货话术
3. 特殊品类约束：
   - 美妆/护肤/保健品：不承诺功效，仅解读公开成分，提示"效果因人而异"
   - 母婴用品：禁用"绝对安全、零风险"，提示关注 3C 认证、国标
   - 医疗器械：不替代医嘱，仅做参数对比，提示"遵从医嘱"
   - 食品/生鲜：不承诺口味，提醒生产日期、配料表、过敏风险
   - 二手商品：强调高风险和个体差异，不担保卖家，只提供避坑流程

### 10.3 数据诚实标注

1. 数据为 2016-2018 年巴西数据，标注"用于验证方法论，数值不反映当前"
2. 非实时数据，标注"基于历史数据，仅供参考"
3. 样本少时标注"样本仅 X 条"
4. 无长期记忆（会话内 5 轮，关闭后不记得）

### 10.4 数据纪律

1. 卖家 ID 前缀匹配多个时，诚实提示"前缀不唯一"，不静默取第一个
2. 结论方向正确：不仅数字对，"谁高谁低、谁快谁慢"方向也要对
3. 信息分层：用户侧只给模糊结论，底层精确数据放推理链路（trace）供分析查看

## 十一、对话类意图答复标准

### capability（能力介绍）

- 介绍能做的三件事：判断配送时效、识别卖家风险、对比价格
- 口语化、亲切，可带提问示例
- 不编造不存在的功能

### methodology（方法论）

- 口语解释判断方法（"参考历史订单里大多数人的实际收货时间"）
- 禁止出现 P50、P90、n=、样本数、中位数等内部指标
- 说明"数字是从真实订单数据查出来的，不是编的"

### unsupported（不支持的功能）

- 温和说明"目前还不具备这个功能"，引导回现有能力
- 引导时只能提"时效、价格、卖家风险"三件事，不编造其他功能

### other（无关闲聊）

- 直接陪聊，不拒绝、不跳回购物话题
- 敏感话题（医疗、法律）提醒咨询专业人士
